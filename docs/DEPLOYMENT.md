# Deployment

Four processes and two data stores, deployed on free tiers. This
document says exactly what is compromised to make that free, so nobody
reads the architecture and assumes the deployment matches it.

```
Vercel      the frontend (static)
Render      the API, with the relay and job runner embedded
Atlas       MongoDB
Upstash     Redis
```

---

## The three compromises, stated plainly

### 1. The relay and job runner do not get their own processes

They are separate processes in the design and separate processes in
development. **Render's free tier has no background workers** - they
start at $7/month each - so a free deployment sets `EMBED_WORKERS=true`
and runs both inside the API process.

Nothing in the code changes. Both already export `start()` and only
self-launch when run as a process entry point, so this is a deployment
switch rather than a different build. To undo it: set
`EMBED_WORKERS=false` and add two `type: worker` services.

What is actually lost: the API and the workers now share a CPU and fail
together. On a free tier with one instance, neither of those was
independent anyway.

### 2. The service sleeps

Free Render web services **spin down after 15 minutes of inactivity**,
and the next request waits 30-60 seconds for a cold start.

While it sleeps: prices do not drift, the relay projects nothing, and no
newspaper is written. Everything catches up on wake - the stream is
durable, so nothing is lost - but a demo link that has been idle
overnight will look frozen for the first minute.

This is worth knowing because "prices move on their own" is one of the
things the project claims, and a sleeping instance cannot demonstrate it.

### 3. Redis is billed per command, and the jobs are what spend it

This is the one that actually bites.

Upstash's free tier allows **500,000 commands per month**. That is about
16,000 a day, or **11 a minute sustained**. At the development cadence
the system issues roughly this many while completely idle:

| Source | Cadence | Commands/min |
|---|---|---|
| drift tick (8 goods) | every 1 min | ~18 |
| revaluation | every 2 min | ~17 |
| relay `XREADGROUP BLOCK 5s` | continuous | ~12 |
| | | **~47** |

47 a minute is 68,000 a day. **The free tier would be exhausted in about
a week with nobody playing.**

`render.yaml` therefore slows everything down in production:

| Setting | Development | Production | Commands/min |
|---|---|---|---|
| `DRIFT_CRON` | every 1 min | every 5 min | ~4 |
| `REVALUE_CRON` | every 2 min | every 10 min | ~2 |
| `NEWSPAPER_CRON` | hourly | every 6 hours | ~0 |
| `RELAY_BLOCK_MS` | 5,000 | 30,000 | ~2 |
| | | | **~8** |

About 11,500 a day idle, leaving roughly a third of the quota for actual
play. Combined with the spin-down - which stops the jobs entirely while
nobody is visiting - this is comfortable in practice.

**What the slower cadence costs:** prices step every five minutes rather
than every minute, so a chart is chunkier. The leaderboard can be ten
minutes stale. Neither affects correctness; both are visible.

## Steps

### 1. Redis (Upstash)

Create a free Redis database. It must support `EVAL` and streams -
Upstash does; both are load-bearing here, not optional.

Copy the `rediss://` URL.

### 2. MongoDB (Atlas)

Already set up. Under **Network Access**, allow `0.0.0.0/0` - Render's
outbound IPs are not fixed on the free tier, so an IP allow-list cannot
work.

### 3. API (Render)

Connect the repository. `render.yaml` is picked up automatically.

Set these in the dashboard, not in the file:

| Variable | Value |
|---|---|
| `MONGO_URI` | the Atlas connection string |
| `MONGO_DB_NAME` | `tgc` |
| `REDIS_URL` | the Upstash `rediss://` URL |
| `WEB_ORIGIN` | the Vercel URL, once step 4 exists |

`JWT_SECRET` is generated by Render. Do not set it by hand, and do not
reuse the development one.

Then seed the market once, from the Render shell:

```bash
npm run seed --workspace=@tgc/api
```

### 4. Frontend (Vercel)

Import the repository. Root directory `packages/web`. Set:

| Variable | Value |
|---|---|
| `VITE_API_URL` | the Render URL, e.g. `https://tgc-api.onrender.com` |

Then go back to Render and set `WEB_ORIGIN` to the Vercel URL. Without
it the browser blocks every request, because CORS is an explicit
allow-list rather than a wildcard - a wildcard would let any site on the
internet make authenticated requests with a stolen token.

## If Redis is ever lost

Nothing needs restoring from a backup. The trade ledger is in MongoDB,
and the whole market reconstructs from it:

```bash
npm run rebuild --workspace=@tgc/api
```

This is worth knowing for a free tier specifically: some free Redis
offerings have no persistence at all and are wiped on restart. That would
normally disqualify them. Here it is survivable, and demonstrating the
rebuild is more interesting than never needing it.

## What to check after deploying

```bash
curl https://<api>/health          # both stores connected
curl https://<api>/goods           # eight goods with prices
```

Then open the Vercel URL, register, and buy something. If the header
balance changes and the price moves, every layer is working: the Lua
script executed, the stream took the trade, and Redis served the new
price.

Wait five minutes and reload the market - if prices have moved without
anyone trading, the embedded job runner is alive too.
